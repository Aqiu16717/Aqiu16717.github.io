为什么 MySQL 更新主键是大忌，而 PG/Oracle 却很轻松？

aq1u
2026-05-08 (Updated: 2026-05-08)
数据库
InnoDB, MySQL, Oracle, PostgreSQL, 主键, 存储引擎, 数据库

同一条 UPDATE users SET id = 999 WHERE id = 1，在 MySQL 里可能是性能灾难，在 PostgreSQL 里却平平无奇。根源不在 SQL 层，而在数据怎么落盘。

1. 现象：同样的语句，不同的代价

在 MySQL InnoDB 中，这条语句可能触发：

  • 聚簇索引中删除旧行、插入新行（B+ 树物理移动）
  • 两条二级索引（idx_name、idx_email）的全部相关条目更新
  • 可能的页分裂和锁升级

在 PostgreSQL / Oracle 中，这条语句通常只触发：

  • 主键索引中一个指针的变更
  • 行本身原地更新或同页内迁移
  • 二级索引几乎不受影响

差距的根源，是IOT 与堆表两种存储结构对”主键”截然不同的定义。

2. MySQL：主键即数据，一动全动

2.1 聚簇索引决定了行的物理位置

InnoDB 中，主键索引就是表。数据行按主键顺序紧凑地存放在 B+ 树的叶子节点里：

id=1 这行数据的物理位置由主键值决定。你把它改成 id=999，等于说：

这行数据在 B+ 树中的”坐标”变了，必须物理搬家。

具体做什么？

  1. 在聚簇索引中删除旧记录：找到 id=1 的叶子节点，标记删除
  2. 在聚簇索引中插入新记录：从根开始遍历，找到 id=999 该在的位置，插入
  3. 如果目标页满了：触发页分裂，树结构调整，连锁反应

这不是”改一个字段”，而是”删一行 + 插一行 + 可能拆页”。

2.2 二级索引的级联更新

InnoDB 的二级索引不存物理地址，存的是主键值：

你把 id=1 改成 id=999，所有指向它的二级索引条目全部失效。InnoDB 必须：

  • 扫描所有二级索引（本例中是 idx_name 和 idx_email）
  • 找到 PK Value = 1 的条目
  • 把它们改成 PK Value = 999

如果有 5 个二级索引，就要改 5 棵 B+ 树。主键越长（比如 UUID），二级索引越大，这个代价越高昂。

2.3 更新主键的代价清单

操作 MySQL InnoDB
聚簇索引 删除 + 插入，可能页分裂
二级索引 全部级联更新（N 个索引改 N 次）
锁范围 可能从记录锁升级为间隙锁或 Next-Key Lock
日志量 undo + redo 双重放大
页分裂 主键跨度大时大概率触发

3. PG/Oracle：主键只是索引，行住在堆上

3.1 堆表中的行有固定”门牌号”

PostgreSQL 和 Oracle 默认使用堆表。数据随便堆在磁盘页里，主键只是一个普通索引，负责把 id 映射到行的物理地址（TID/ROWID）：

id=1 那行住在 (page_2, slot_1)，这个物理地址不会因为主键值改变而搬家。

更新主键时：

  1. 堆中的行原地更新：page_2, slot_1 里的 id 字段直接改成 999（或创建新版本行）
  2. 主键索引更新：删除 id=1 → (page_2, slot_1)，插入 id=999 → (page_2, slot_1)
  3. 二级索引不动：因为二级索引存的是物理地址 (page_2, slot_1)，不是主键值

3.2 PostgreSQL 的 HOT 进一步优化

如果更新的恰好是主键列以外的字段，PostgreSQL 的 HOT（Heap-Only Tuple） 机制可以在同一页内完成：

  • 新行版本直接插在同一个堆页的空闲空间里
  • 所有索引完全不需要更新
  • 只需要维护页内的行指针链

虽然更新主键本身用不了 HOT（因为主键索引必须改），但堆表的架构决定了：只有主键索引需要动，二级索引全程旁观。

3.3 更新主键的代价清单

操作 PG / Oracle (堆表)
数据行 原地更新或同页内新位置，不跨页搬家
主键索引 更新一个指针条目
二级索引 完全不受影响
锁范围 通常只涉及目标行和索引页
日志量 远小于 IOT 的删+插

4. 一个具体的对比实验（思想实验）

假设表有 100 万行，5 个二级索引，更新一行主键：

代价项 MySQL InnoDB PostgreSQL
聚簇/主键索引操作 删 + 插，可能页分裂 更新一个指针
二级索引操作 5 个索引各改 1 条 = 5 次 B+ 树更新 0 次
涉及的 B+ 树 1（聚簇）+ 5（二级）= 6 棵 1 棵（主键索引）
最坏情况 页分裂导致大量页 IO 仅单页内的行版本链

差距是几倍到几十倍，取决于二级索引数量和主键长度。

5. 为什么 MySQL 不改成堆表？

这不是设计缺陷，而是权衡。

InnoDB 选择 IOT 是为了换取：

  • 主键查询极快：主键索引即数据，无需回表
  • 主键范围查询顺序 IO：相邻主键的行物理相邻

代价就是：主键一旦确定，尽量不要改。这也是 MySQL 社区反复强调”主键设计很重要”的根本原因。

PostgreSQL 选择堆表是为了换取：

  • 写入灵活：插入任意位置，更新自由
  • MVCC 自然：多版本直接堆在页内，索引负担轻

代价是：主键查询多一次回表（索引 → TID → 堆页）。

两种设计都有代价，只是代价换在了不同的地方。

6. 工程建议

MySQL 用户

  • 主键设计为永不更新的列：自增 ID、业务无关的 UUID、雪花算法 ID
  • 如果业务需要”逻辑上的主键变更”，用软删除 + 新插入或增加一个独立的业务编码列
  • 绝对避免用可能变更的字段（如手机号、邮箱）做主键

PostgreSQL / Oracle 用户

  • 虽然更新主键代价低，但也不是零成本（主键索引还是要更新的）
  • 如果主键被大量外键引用，级联更新外键的开销依然存在
  • 最佳实践同样是”主键不变”，只是容错空间比 MySQL 大得多

7. 总结

维度 MySQL InnoDB (IOT) PG / Oracle (堆表)
数据与主键关系 主键即数据，物理绑定 主键是索引，行独立存在
更新主键时行的命运 物理搬家（删旧 + 插新） 原地不动，只改字段值
二级索引是否受累 全部级联更新 不受影响
页分裂风险 高（跨页搬家时） 低（同页内完成）
为什么说”大忌” 一动主键，六棵树一起动 只动一棵树

MySQL 更新主键是大忌，不是语法禁止，而是存储结构让它的代价高到不值得。 PG/Oracle 的堆表把数据和索引解耦，主键从”房屋的承重墙”变成了”门牌号”，自然可以随意更换。

底层存储结构决定了上层的使用哲学——这句话在数据库世界里永远成立。
