堆表 vs IOT：PG/Oracle 与 MySQL 的存储哲学

aq1u
2026-05-08 (Updated: 2026-05-08)
数据库
InnoDB, MySQL, Oracle, PostgreSQL, 存储引擎, 数据库

关系型数据库的表数据在磁盘上怎么放，看似是底层细节，却直接决定了查询性能、空间管理和并发行为的方方面面。PostgreSQL、Oracle 默认用堆表（Heap Table），而 MySQL InnoDB 默认用索引组织表（IOT，Index-Organized Table）。两种设计没有绝对的优劣，只有不同的取舍。

1. 核心概念

1.1 堆表（Heap Table）

堆表把数据当作一个无序的数据页集合。你插入一行，数据库就把它放到当前有空闲空间的某个页里，完全不关心主键是什么、插入顺序如何。

代表：PostgreSQL（始终）、Oracle（默认）、SQL Server（堆表可选）

1.2 IOT / 聚簇索引表

IOT 把数据直接存在主键索引的叶子节点里。表的数据按主键顺序物理（或逻辑）有序排列，主键索引就是数据本身。

代表：MySQL InnoDB（始终）、Oracle（IOT 可选）、PostgreSQL（仅类似物化视图，非原生）

2. 查询性能对比

2.1 主键精确查询

场景 堆表（PG/Oracle） IOT（MySQL InnoDB）
步骤 查主键索引 → 拿到 TID/ROWID → 再去堆页读整行 查主键索引 → 叶子节点直接就是数据
IO 次数 至少 2 次（索引页 + 数据页） 通常 1~2 次（索引树高度）
** winner** ✅ IOT 更优

堆表多了一次”回表”（Heap Fetch），这是堆表绕不开的代价。

2.2 二级索引查询

这是两者差异最显著的地方。

堆表的二级索引：

IOT 的二级索引（InnoDB 称为 Secondary Index）：

场景 堆表（PG/Oracle） IOT（MySQL InnoDB）
回表方式 用物理地址直接定位堆页 用主键值去主键索引再查一次（回表）
索引大小 较小（物理地址通常 4~6 字节） 较大（主键值可能很长，如 UUID 36 字节）
物理地址变了的处理 必须更新所有索引（HOT 优化可缓解） 不受影响，二级索引存的是逻辑主键
覆盖索引效果 更好（索引小，更容易全放内存） 稍差（索引大，但主键查询省一次 IO）

PostgreSQL 的 HOT（Heap-Only Tuple）：更新非索引列时，PG 可以在同一页内创建新版本行，不更新任何索引。这是堆表对抗索引更新开销的利器。

2.3 范围查询

维度 堆表 IOT
数据局部性 差。id 相邻的行可能散落在不同页 ✅ 极好。id 相邻的行物理相邻，顺序 IO
缓存友好性 预读困难，随机 IO 多 顺序扫描，预读命中率高
** winner** ✅ IOT 大胜

这也是 OLAP 场景下，MySQL 主键范围查询通常比 PG 更友好的原因。当然，PG 可以通过**聚簇（CLUSTER）**命令临时重排堆表，但这是离线操作且需要维护。

2.4 全表扫描

维度 堆表 IOT
数据读取 按物理页顺序读，连续 IO 按主键顺序读，逻辑上可能跳跃（页分裂后）
空间密度 可能有碎片，但通常较紧凑 主键顺序导致页分裂，可能有空洞
** winner** ✅ 堆表略优

堆表的全表扫描通常是更纯粹地顺序读磁盘页。IOT 因为 B+ 树的结构，叶子节点可能不连续，顺序性稍差。

3. 写入性能对比

3.1 插入新行

维度 堆表 IOT
插入位置 随便找个有空位的页塞进去 必须按主键顺序插入到正确位置
页分裂 仅当页满时分裂当前页 插入中间位置可能触发页分裂和级联调整
主键选择影响 几乎没有 极大。自增主键顺序插入最快，UUID 随机主键是灾难
并发插入 多个事务可并发向不同页插入 自增主键可能导致”尾部热点”竞争
** winner** ✅ 堆表更灵活

MySQL 的隐式主键：如果你建表时不指定主键，InnoDB 会自动生成一个 6 字节的隐藏主键（row_id），这同样是一个 IOT。

3.2 更新操作

更新非索引列：

维度 堆表 IOT
行迁移 原地更新或同页内新位置（HOT） 原地更新，数据量在页内变化大时可能触发页分裂
索引维护 HOT 优化下无需更新任何索引 只需更新涉及的二级索引
** winner** ✅ 堆表 + HOT 很高效

更新主键：

维度 堆表 IOT
物理移动 行不动，只改主键索引里的指针 ❌ 数据行必须在 B+ 树中物理移动位置
代价 低 高：删除旧位置 + 插入新位置 + 更新所有二级索引
** winner** ✅ 堆表完胜

这也是为什么 MySQL 中更新主键是大忌，而 PG/Oracle 中改主键相对轻松。

更新二级索引列：

维度 堆表 IOT
需要更新 该二级索引 + 可能的其他二级索引 该二级索引 + 可能的其他二级索引
额外代价 如果行被迫迁出本页，所有索引都要更新 无额外代价（因为二级索引存的是主键，不受物理位置影响）
** winner** 各有优劣

3.3 删除

维度 堆表 IOT
PG 标记删除（MVCC 版本链），VACUUM 异步清理 标记删除，purge 线程异步清理
Oracle 标记删除，后台进程清理或插入时重用 类似
空间回收 需要专门维护（VACUUM / 段收缩） 页内合并/分裂自然调整
** winner** 各有优劣

4. 空间与碎片

4.1 空间利用率

维度 堆表 IOT
页填充率 通常较高（插入随意填充） 顺序插入时很高；随机插入时页分裂频繁，可能有 50% 填充率
碎片来源 更新/删除后留下的空洞 页分裂导致的半满页
整理方式 VACUUM FULL、ALTER TABLE ... SHRINK SPACE OPTIMIZE TABLE（重建表）

4.2 表与索引的关系

维度 堆表 IOT
数据存储 表（堆）是独立的，索引是附加结构 数据存储在主键索引里，表不能脱离主键存在
主键是否必须 不必须（但强烈建议有） 必须（显式或隐式）
无主键的表 完全正常，堆上直接操作 InnoDB 自动生成 6 字节隐藏主键
索引数量影响 每多一个索引，更新代价线性增加 同样增加，但二级索引通常更大

5. 一些具体场景

5.1 覆盖索引（Covering Index）

维度 堆表 IOT
是否需要回表 如果索引包含所有查询列，则不需要 如果二级索引包含所有查询列，则不需要
索引大小 较小，更容易实现纯内存覆盖索引 较大，但如果查询列少也能覆盖
实际表现 PG 的 Index-Only Scan 非常高效 InnoDB 的 Covering Index 也很高效

5.2 没有主键的查询表 / 日志表

维度 堆表 IOT
适用性 ✅ 非常适合。直接堆插，无额外维护 必须造一个隐藏主键，无端增加开销
顺序写入 日志顺序追加，性能极好 自增主键也能顺序写，但多了一层 B+ 树维护
典型场景 PG 的日志表、临时表、大字段表 MySQL 也常用，但不如堆表自然

5.3 主键高频范围扫描的 OLTP

维度 堆表 IOT
订单表按 user_id 查近期记录 索引查到一堆 TID，回表随机 IO ✅ 主键索引直接顺序读，性能极佳
典型系统 需要额外优化（如 pg_cluster） MySQL 天生擅长此类查询

6. 能不能换一条路？

6.1 Oracle：两者皆可

Oracle 提供了真正的 IOT 语法：

Oracle 用户可以根据访问模式自由选择，这是灵活性最高的方案。

6.2 PostgreSQL：原生只有堆表

PG 没有原生 IOT，但有几个 workaround：

  • CLUSTER 命令：按某个索引顺序离线重排堆表。表变为逻辑有序，但仍是堆结构，且后续插入会打乱顺序。

  • 覆盖索引 + Index-Only Scan：用多级索引模拟 IOT 的查询效率。

  • 表继承 + 分区：按范围分区可以让数据在分区键上保持局部有序。

6.3 MySQL：原生只有 IOT

InnoDB 不支持堆表。如果你确实需要堆表语义：

  • 用自增主键模拟顺序插入，避免随机主键的碎片
  • 用 ROW_FORMAT=COMPRESSED 或 DYNAMIC 优化空间
  • 考虑 MyISAM（不推荐，不支持事务），或者 MariaDB 的 Aria 引擎

7. 总结

对比维度 堆表（PG / Oracle） IOT（MySQL InnoDB）
数据组织 无序堆页集合 主键 B+ 树叶子节点即数据
主键查询 索引 + 回表（2 次 IO） 索引即数据（1~2 次 IO） ✅
二级索引 存物理地址，小而快 存主键值，大但不受物理位置影响
范围查询 回表随机 IO 顺序 IO，缓存友好 ✅
插入性能 快，任意位置插入 依赖主键选择，随机主键性能差
更新主键 轻量 昂贵（物理移动行）
更新非索引列 HOT 优化下极高效 ✅ 正常
全表扫描 顺序读，略优 ✅ B+ 树叶子遍历
碎片问题 堆页空洞 页分裂导致的半满页
无主键表 完全支持 ✅ 自动生成隐藏主键
空间密度 通常较高 顺序插入高，随机插入低

一句话概括

  • 堆表把数据和索引彻底解耦：表是表，索引是索引。插入自由、更新灵活，但查主键和范围查询要多一次回表。
  • IOT把数据和主键焊在一起：主键即表。主键查询和范围查询飞快，但插入受主键顺序约束，更新主键代价高昂。

这也解释了为什么 MySQL 社区反复强调”主键设计很重要”，而 PostgreSQL 社区对主键的态度相对宽松——底层存储结构决定了上层的使用哲学。
